# Manus 프로젝트 설정에 붙여넣을 문구

Manus 웹앱의 프로젝트 지침(시스템 프롬프트 / Custom Instructions) 항목에 아래 블록을 그대로 붙여넣으세요.
저장소 구조가 바뀌면(`todo.md` 위치나 형식 변경 등) 이 문구도 같이 업데이트해야 합니다.

---

```
[협업 동기화 규칙 — 반드시 준수]

이 저장소(essay-master2)는 Local(사용자 본인 + Claude Code), Codex, Manus(나) 세 주체가
동시에 작업한다. 나는 다른 두 주체보다 훨씬 자주(약 1시간 간격) 커밋하므로,
아래 규칙을 지키지 않으면 다른 주체의 작업과 충돌할 가능성이 매우 높다.

1. 작업을 시작하기 전, 저장소 루트의 todo.md 파일에서
   "## 진행 중 (Claim)" 섹션을 먼저 읽는다.

2. 이미 다른 주체(Local 또는 Codex)가 Claim한 파일/기능 영역과 겹치는 작업은
   시작하지 않는다. 겹치는 경우, 아직 배정되지 않은 다른 작업을 먼저 진행하거나
   해당 작업을 보류한다.

3. 겹치지 않는 작업임을 확인했다면, 실제 코드를 수정하기 전에 먼저 아래 형식으로
   todo.md의 "## 진행 중 (Claim)" 섹션에 한 줄을 추가하고, 그 변경만 담아
   별도로 커밋한다:

   - [Manus] <작업 내용 한 줄 요약> — 시작 <YYYY-MM-DD HH:MM>

   커밋 메시지 형식: docs: claim <작업 요약> [manus]

4. 작업을 마치면 해당 Claim 항목을 todo.md의 "## 완료" 섹션으로 옮기고 커밋한다.

5. 커밋은 가능한 한 작은 단위로 나눈다. 하나의 커밋에 서로 관련 없는 변경
   (예: 질문은행 로직 + UI 스타일 + 문서 수정)을 섞지 않는다. 커밋 메시지에
   건드린 파일/기능 범위를 구체적으로 적는다.
   예: "Checkpoint: question-bank QA 로직 개선 (server/questionGeneration.ts)"
   (파일명을 명시하지 않은 채 "Checkpoint: 여러 기능 업데이트" 같은 커밋은 지양)

6. 세션이 1시간 이상 이어지는 경우, 새 커밋을 만들기 전에 origin/main의 최신
   커밋 로그를 다시 확인한다. 그 사이 다른 주체가 같은 영역을 이미 수정했을 수
   있으므로, 겹치는 변경이 보이면 먼저 반영한 뒤 이어서 작업한다.

7. schema.ts, db.ts, routers.ts처럼 여러 기능이 동시에 참조하는 핵심 파일은
   가능하면 한 세션 내에서 최소한으로만 수정하고, 수정 이유를 커밋 메시지에
   명확히 남긴다.
```

---

## 참고

- 이 문구는 "브랜치 분리"까지는 강제하지 못합니다. Manus가 브랜치를 만들고 PR을 여는 방식을 지원한다면, 추가로 "항상 manus/work 브랜치에서 작업하고 PR을 연다"는 문장을 넣는 것이 더 강력합니다. 지원 여부를 Manus 설정 화면에서 먼저 확인해보세요.
- 이 문구를 넣은 이후에도 Manus가 Claim 없이 커밋하는 경우가 반복되면, 문구가 무시되고 있다는 뜻이므로 로컬 쪽 체크리스트(2단계, alias 스크립트)로 방어선을 한 겹 더 두는 게 안전합니다.
