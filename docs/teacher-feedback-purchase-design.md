# 교사 첨삭지도 건별 결제 설계 (앱 안 추가 결제)

> 상태: **설계안(미구현)**. 구현 전에 아래 「확정이 필요한 결정」 5가지를 정해야 합니다.
> 기준: 『가격 및 환불정책』 1·2·4·6·7·8·11조, 현재 코드(2026-10-13).
> 외부 표기(요금 페이지의 가격권 3종 + "이용권 결제자만 신청할 수 있습니다.")는 이미 반영했고, 신청 기능이 열리기 전에는 "신청 기능 준비 중"으로 표시합니다(`TEACHER_FEEDBACK_PURCHASE_OPEN`).

## 1. 목표

- 교사 첨삭을 **이용권과 별개의 건별 상품**으로, **서비스 안에서 추가 결제**해 신청한다.
- **이용권 결제자만** 신청할 수 있다. 무료 체험만 쓰는 사용자는 신청할 수 없다.
- 상품(정책 1조): 핵심 3,900원 / 일반 6,900원 / 종합 9,900원 (건당).
- 정책 4조: AI 이용 횟수에 따라 교사 지도비가 자동 청구되지 않는다. 신청한 건만 제공한다.

## 2. 현재 구조 (확인한 사실)

| 항목 | 현재 |
|---|---|
| 첨삭 요청 방식 | 신청 개념이 없다. 학생이 논술을 제출(`essay_submission.status = submitted`)하면 **배정된 교사**(`users.teacherId`)가 첨삭한다 |
| 비용 | 개인 학생은 **무료**. 기관 계약 반이면 계약의 '첨삭' 예산을 차감 |
| 교사 권한 검사 | `assertTeacherEssayAccess`: 승인된 교사 + 그 학생의 담당 교사만 (`server/routers.ts`) |
| 결과 저장 | `teacher_feedback`(점수·코멘트), 글당 1건(`CONFLICT` 처리) |
| 정산 | 교사 활동 `essay_feedback`(기본 3,000원/건) 등을 월 정산. 활동 시점 정책을 장부(`teacher_activity_accounting`)에 고정 |
| 결제 | `payment_orders`·제공자 추상화·임시(mock) 결제, 환불은 관리자(`adminRefund`) |

따라서 새 기능은 **"신청 → 결제 → 교사 작업 → 전달"** 단계를 새로 만들고, 기존 첨삭 작성 화면과 정산을 그 위에 연결하는 방식이다.

## 3. 사용자 흐름

```
[학생] 제출한 논술 → '교사 첨삭 신청'
   ① 상품 선택(핵심/일반/종합) · 핵심은 평가항목 선택
   ② 안내 확인: 피드백 범위·분량, 완료 예정일, 담당 교사, 환불 기준(전달 전 취소 시 전액)
   ③ 결제(앱 안, 임시 결제 → 추후 PG)            → 상태: paid
[시스템] 담당 교사에게 알림(첨삭 대기열)
[교사] 대기열에서 열기(in_progress) → 기존 첨삭 작성 화면에서 작성·제출
[시스템] 첨삭 등록 시 신청을 delivered로 바꾸고 학생에게 알림, 정산 장부 기록
[학생] 전달 전에는 언제든 취소 → 전액 환불
```

### 신청 가능 조건 (서버에서 모두 검사)

1. 학습자 계정(학부모·교사·관리자 불가)
2. **이용 중인 유료 이용권이 있음**(→ 결정 ①)
3. 본인 논술이고 `submitted` 상태이며 본문이 비어 있지 않음(정책 4조: 필수자료 부족 시 신청을 받지 않고 필요한 자료를 안내)
4. 같은 글에 진행 중인 신청이 없음(중복 결제 방지)
5. 첨삭을 맡을 **승인된 교사**가 있음(담당 교사가 없으면 신청 불가 안내 → 마이페이지에서 담당 교사 선택)
6. 기관 계약이 비용을 부담하는 학생은 이 경로가 아니라 기존 기관 예산 경로(→ 결정 ②)

## 4. 데이터 모델

새 테이블 `teacher_feedback_requests` (마이그레이션 0055, `CREATE TABLE`이라 기존 적용 스크립트로 처리 가능):

| 컬럼 | 설명 |
|---|---|
| `id` | PK |
| `userId` | 신청 학생 |
| `essayId` | 대상 논술 |
| `productKey` | `tf_core` / `tf_standard` / `tf_comprehensive` (`shared/plans.ts`) |
| `priceKrw` | 결제 시점 가격(상품 가격이 바뀌어도 보존) |
| `scopeJson` | 핵심 첨삭의 선택 평가항목 등 신청 범위 |
| `teacherId` | 배정된 교사(신청 시점의 담당 교사) |
| `status` | `paid` → `in_progress` → `delivered` / `cancelled` / `refunded` |
| `orderId` | `payment_orders.id` (환불·정산 추적) |
| `dueAt` | 완료 예정일(결제 시점에 고정해 안내) |
| `deliveredAt`, `teacherFeedbackId` | 전달 시각, 결과(`teacher_feedback.id`) |
| `cancelledAt`, `cancelReason` | 취소 정보 |
| `createdAt`, `updatedAt` | |

- 인덱스: `(userId)`, `(teacherId, status)`, `(essayId)`.
- `payment_orders`는 **재사용**한다: `planKey`에 `tf_*`를 넣는다(`getPlanName`이 이미 이름을 알아본다). 이용권 결제 API(`startCheckout`)는 `tf_*`를 받지 않는다(테스트로 보장).
- 결제 확정은 주문 `paid` 처리와 신청 행 생성을 **한 트랜잭션**으로 한다(기존 `confirmOrderAndActivateSubscription`과 같은 방식, 중복 처리 방지).

## 5. 서버(API) 설계

| 프로시저 | 권한 | 내용 |
|---|---|---|
| `teacherFeedbackRequest.quote` | 학습자 | 선택 상품의 가격·완료 예정일·담당 교사·신청 가능 여부와 이유(결제 전 안내용) |
| `teacherFeedbackRequest.create` | 학습자 | 위 조건 검사 → 주문 생성 → 제공자 결제 → 성공 시 신청 `paid` 확정 + 교사 알림 |
| `teacherFeedbackRequest.mine` | 학습자 | 내 신청 목록·상태 |
| `teacherFeedbackRequest.cancel` | 학습자 본인 | `delivered` 전이면 취소 → 제공자 환불 → 주문 `refunded`, 신청 `cancelled` |
| `teacherFeedbackRequest.queue` | 승인 교사 | 내게 배정된 `paid`/`in_progress` 신청 |
| `teacherFeedbackRequest.start` | 담당 교사 | `paid` → `in_progress` |
| (기존) `teacherFeedback.create` | 담당 교사 | 첨삭 등록 시 해당 글의 신청을 `delivered`로 전환 + 학생 알림 + 정산 장부 기록 |
| `adminTeacherFeedbackRequests` | 관리자 | 전체 신청·지연 건 조회, 강제 환불 |

- 환불은 **전달 전 전액**(정책 7조): 교사 배정·작업 착수·교사비 지급을 이유로 공제하지 않는다.
- 전달 후에는 단순 변심 환불이 없다. 단, 정책 8조에 따라 **약속한 범위·완료 예정일을 지키지 못한 건**은 학생이 '무료 보완' 또는 '환불'을 선택할 수 있어야 한다 → `dueAt` 경과 시 학생 화면에 선택 버튼(환불은 즉시 환불, 보완은 교사에게 재작업 요청).
- 결제·취소 요청은 기존 요금 제한(`checkout` 한도)을 재사용한다.
- 관리자 환불(`adminRefund`)이 교사 첨삭 주문이면 신청 상태도 `refunded`로 바꾸도록 `markOrderRefunded`를 확장한다.

## 6. 정산(교사 지급) 연동

- 현재 `essay_feedback`는 건당 3,000원 단가다. 상품 가격이 3,900/6,900/9,900원으로 나뉘므로 **교사 지급액 구조를 정해야 한다**(→ 결정 ③). 후보:
  - A) 상품별 단가: `settlement` 활동 유형을 `essay_feedback_core/standard/comprehensive`로 늘리고 단가를 따로 둔다.
  - B) 결제금액 비율: 결제금액의 일정 비율을 지급한다(비율은 관리자 설정).
- 어느 쪽이든 교사 지급(교사비)을 이유로 **환불을 거절하거나 공제하지 않는다**(정책 7·8조).
- 정산 장부(`teacher_activity_accounting`)에는 신청이 `delivered`된 시점에 활동을 기록하고, 취소·환불된 신청은 정산 대상이 아니다.
- 기존에 무료로 하던 담당 학생 첨삭(신청 없이 등록)은 과도기 처리가 필요하다(→ 결정 ④).

## 7. 화면 설계

- **요금 페이지**(반영 완료): 가격권 3종 + "이용권 결제자만 신청할 수 있습니다." + (오픈 전) "신청 기능 준비 중".
- **학생**: 제출한 논술 화면/AI 첨삭 결과에 `교사 첨삭 신청` 버튼 → 신청 모달(상품 선택·안내·결제) → 내 신청 목록(상태·완료 예정일·취소·지연 시 선택).
  - 이용권이 없으면 버튼 대신 "이용권 결제자만 신청할 수 있어요" + 결제 화면 링크.
- **교사**: 마이페이지에 '첨삭 신청 대기열'(종류·완료 예정일·남은 시간), 열기 → 기존 `/teacher-feedback/:essayId`.
- **관리자**: `/admin/billing`에 교사 첨삭 신청 탭(결제·진행·지연·환불).
- 구매 기능을 열 때 `TEACHER_FEEDBACK_PURCHASE_OPEN`을 `true`로 바꾼다.

## 8. 확정이 필요한 결정

| # | 결정 | 제안 |
|---|---|---|
| ① | **'이용권 결제자'의 기준** | **현재 이용 중인 유료 이용권이 있는 사용자**(30일 상품은 '유료 이용 시작'을 눌러 기간 안, 추가권은 90일 안). 결제만 하고 시작 전이면 신청 불가(시작 안내). 결제 이력만으로 영구 허용하는 방식은 비권장 |
| ② | **기관 계약 학생** | 개인 결제 경로를 막고 기존 기관 예산 경로를 유지 |
| ③ | **교사 지급 방식** | 상품별 단가(A) 또는 결제금액 비율(B), 구체 금액 |
| ④ | **기존 무료 첨삭의 전환** | 개인 학생은 신청·결제가 있어야 첨삭. 이미 제출되어 대기 중인 건은 무료로 마무리. 교사의 반 과제 채점·워크북 첨삭·기관 반은 영향 없음 |
| ⑤ | **완료 예정일 기본값** | 신청일 기준 3영업일(관리자 설정 가능). 필수자료 부족 시 접수 전 안내 |

## 9. 구현 단계 제안

1. **2a**: 마이그레이션 0055, 신청·결제·취소·전달 서버, 학생 신청/목록, 교사 대기열, 알림. 임시 결제 기준.
2. **2b**: 정산 연동(결정 ③), 관리자 탭, 지연 시 보완/환불 선택, 관리자 환불 연동.
3. **2c**: 실제 PG 연동 시 결제 흐름 교체(제공자 추상화가 이미 있어 신청 로직은 그대로).

테스트 계획: 신청 조건(이용권·본인 글·중복·교사 없음), 결제 실패 시 신청 미생성, 취소·환불 멱등, 전달 시 정산 기록, 타인 신청 접근 차단, 이용권 결제 API로 `tf_*` 결제 불가.

## 10. 위험·주의

- 정책에 "유료 전체 문제은행", "교사 첨삭 완료 예정일" 등이 이미 공개되어 있어, **오픈 전에 구현 범위와 문구를 맞춰야 한다**(요금 페이지는 "준비 중"으로 표기).
- 실제 PG가 아직 없다(임시 결제). 교사 첨삭을 실제 금액으로 받기 전에 PG 연동과 환불 처리가 필요하다.
- 교사 지급 단가를 정하기 전에는 정산 연동을 구현하지 않는다.
